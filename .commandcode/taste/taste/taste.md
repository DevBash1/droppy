# Taste
- When building against a third-party platform, implement from that platform's official documentation (e.g., "use docs from docs.salesive.com") rather than guessing API shapes or payloads. Confidence: 0.7
- When an app is repurposed/rebranded, expects every trace of the old product to be gone — visible screens (install splash, titles), dead components/icons, stale comments, webhook maps, and config/db names — not just the main UI. Flags leftover remnants promptly. Confidence: 0.6
- When given a brand asset (e.g., logo.png), expects it to be used in the actual UI (install splash hero, app header) and served by the app, not just referenced or replaced with a placeholder glyph. Confidence: 0.7
- Expects theme colors to be derived from the brand logo (read its colors, e.g., blue primary + orange accent), and a theme change means a full app-wide redo of styling and layout — Tailwind palette, shared CSS surfaces, nav, buttons, avatars, states, splash screen — with zero stale old-theme classes left in the build. Confidence: 0.7
- Builds e-commerce / dropshipping tooling for the Nigerian market, with Naira (NGN) currency conversion a standard part of the feature set. Confidence: 0.6
- Accepts the recommended server-side architecture when offered options — heavy/privileged work (scraping, token handling, API calls) stays on the server so secrets never ship in the browser bundle. Confidence: 0.5
- Wants professional, plain UI copy: explicitly asked to remove em-dashes from user-visible strings (kept out of the interface text; plain punctuation preferred over typographic flourishes). Confidence: 0.7
- Wants user-imported data persisted client-side in localStorage (keyed per shop) so imported products survive reloads and appear instantly in the catalog even before/without the server list. Confidence: 0.5
- Wants frequently-reused form inputs/settings (e.g., the markup % field) persisted client-side in localStorage (keyed per shop) and restored on load, so the user doesn't have to re-enter them on every visit ("persist the markup so its not always reinputted"). Confidence: 0.7
- Expects page scrolling to live in the content area — a pinned header with the shell clipped (`h-screen overflow-hidden`) and a scrollable `<main>` (`overflow-y-auto min-h-0 flex-1`) — so content taller than the viewport is never clipped. Confidence: 0.5
- Wants bug fixes paired with proactive visual polish ("fix it and make the UI better"): frosted/sticky header with bottom border, shadowed cards with hover lift, bolder page titles with relaxed subtitles, and pill/status chips — not just the minimal fix. Confidence: 0.5
- When an existing third-party dependency fails for a supported platform (e.g., a scraper returning only the image for AliExpress), expects a search for and adoption of a purpose-built, actively-maintained alternative package — evaluated for Node/engine-version compatibility and dependency weight before installing — rather than patching around the broken one. Confidence: 0.7
- Reports bugs with a concrete repro URL and expects the fix to be verified end-to-end against that exact input (e.g., scraping the precise product link through the real server route, checking price/images/description), not a synthetic sample. Confidence: 0.6
- Prefers long-lived auth sessions: explicitly asked to extend the session/cookie TTL from 7 days to 1 month (30 days) so users aren't logged out frequently. Confidence: 0.7
- Expects the UI to be mobile-responsive: explicitly asked to "fix UI for mobile" — header/nav should wrap on small screens, multi-column grids collapse to one column, and control rows wrap instead of overflowing. Confidence: 0.6
- Wants scraped product images actually displayed in the UI, not just stored: asked "for images, display them" — catalog cards should show a large product image (not a tiny thumbnail) and import previews should show a main image plus a thumbnail strip for all remaining scraped images. Confidence: 0.6
- Gives terse, imperative, multi-part task instructions (e.g., "Make it 1 month, and Fix UI for mobile, then for images, display them." or "scaping and importing button share same loading state, fix it." or "show error in toast." or "Dont show the shimmer, also replace the emoji arrow with real back arrow icon"). Confidence: 0.7
- Dislikes skeleton/shimmer loading placeholders — explicitly asked to remove the shimmer; prefers a simple, lightweight loading state (centered spinner + short status text) over pulsing skeleton blocks while an async step runs. Confidence: 0.5
- Prefers real icon components from the shared icon library over Unicode/emoji text glyphs (e.g., `←` in a button) for UI affordances like back actions. Confidence: 0.6
- Expects upstream/API error messages to be surfaced to the user verbatim in toast notifications — when the backend returns a validation error (e.g., the Salesive "Product validation failed: name: ..." envelope), the exact message should appear as a toast rather than being swallowed or replaced with a generic failure. Confidence: 0.7
- Expects independent async actions to have independent loading/disabled states in the UI — a shared `busy` flag that makes one button spin for another's work is a bug (e.g., scrape vs. import buttons must each reflect only their own spinner and be cross-disabled). Confidence: 0.6
- Prefers custom UI components over native form controls for entity pickers — explicitly asked to replace the native `<select>` category field with a "custom component dropdown": a searchable combobox with a checkmark on the selected option, outside-click/Escape dismissal, and brand-consistent styling. Confidence: 0.7
- Wants inline creation of new records inside pickers — a category dropdown should offer a "create new" flow that POSTs the new record, dedupes case-insensitively against existing entries, appends it to the list, and auto-selects it, so the user never has to leave the current flow. Confidence: 0.6
- Wants the "create new" input in a searchable picker to auto-fill live with the search query when no existing entry matches, so the user doesn't retype the name — while still allowing manual edits to the prefilled value and resetting when the search is cleared or the dropdown closes. Confidence: 0.6
- Prefers final editable product attributes (including category) to live in the preview step of the import wizard — the flow should be paste URL → scrape → preview (name, description, category, price) → import, keeping the earlier setup step minimal. Confidence: 0.5
- Wants scraped HTML descriptions sanitized at the root cause: strips `<script>`/`<style>` blocks entirely (inner content included) before tag-stripping, so vendor-injected JavaScript (e.g., AliExpress `window.adminAccountId=...` leaking into the description) never reaches the product text. Confidence: 0.7
- Wants every form input to carry a helper/hint comment explaining what goes in it — flags any field that's the only one without one ("add come for input of price too"), e.g., the price hint explains the value is the scraped source-currency cost and how the markup % feeds the ₦ conversion. Confidence: 0.5
- Expects the importer to preserve the full structure of the source product, not just the base listing — when the scraped product has variants (SKUs with attributes/price/quantity) or a video, they must be extracted, mapped to the destination platform's payload (variant prices through the same source→NGN + markup conversion as the base price), and surfaced in the preview UI ("Handle variations and video if any"). Confidence: 0.6
